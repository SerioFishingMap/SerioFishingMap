## 1. 文書の目的と読み方

本書は、画面設計からシステムに必要な機能・データ・操作上の条件を整理し、開発範囲と未決事項を関係者間で合意するための要件定義書のドラフトである。画面の配置や装飾を再定義するのではなく、利用者が何を実現できる必要があるかを定める。

元の画面設計はすべて下書きである。本書の「設計記載」は承認済みを意味せず、画面設計に根拠があることを示す。機能の存在が記載されていても、項目や動作の詳細が未確定の場合は、その範囲を明記する。

| 区分 | 意味 |
| --- | --- |
| 設計記載 | 現行の画面設計に機能・方針が明記されている要件 |
| 要確認 | 設計内で仮案・推測・未記入とされている、または資料間で不整合がある事項 |
| 提案 | 要件定義を補完するために本書で追加した案。採用判断が必要 |
| 保留／対象外 | 現行方針で実装を保留している機能、または本ドラフトの基本範囲に含めない機能 |

## 2. システムの目的と対象範囲

### 2.1 目的

利用者が地図・一覧・検索から釣り場や魚の情報を探し、釣果を記録・共有できるWebアプリケーションを提供する。蓄積した釣果を魚・釣り場と関連づけて参照できるようにし、次の釣り場探しや過去の記録の振り返りに利用する。

根拠：[ホーム画面](./画面/SCR-001-home.md)のウェルカムメッセージと各画面概要。利用者数、登録件数、利用頻度などの目標値は未定である。

### 2.2 利用者

当面は全画面を「全ユーザー」向けとし、ログイン・ログアウトを実装しない。未ログイン／会員／本人／管理者による画面の出し分けは行わず、「権限なし」の状態も当面使用しない。

釣果に記録する釣り人・同行者と、認証のためのユーザーアカウントは同一概念として扱わない。釣り人・同行者の識別方法は要確認とする。マスタ追加や編集を誰がどの運用で行うかは、認証保留の方針と整合させて決める必要がある。

根拠：[画面設計 README](./画面/README.md)「権限の扱い」、[釣果登録](./画面/SCR-103-catch-register.md)課題2・3、[マスタ追加](./画面/SCR-501-master-add.md)課題5。

### 2.3 機能範囲

| 範囲 | 対象機能 | 位置づけ |
| --- | --- | --- |
| 基本範囲 | ホーム、横断検索、釣果一覧・詳細・新規登録、魚一覧・詳細、釣り場一覧・詳細、地図 | 現行画面設計に記載。詳細未決事項は第10章で管理 |
| 基本範囲のデータ処理 | 釣果登録に伴う釣行記録の保存 | 釣行の専用画面は設けない |
| 設計対象・具体化待ち | 釣果編集（SCR-104） | 採番済みだが画面設計・デザイン未作成。実装時期と仕様は要確認 |
| 設計対象・方式判断待ち | マスタ追加（SCR-501） | 独立画面か釣果登録時の自動追加かを含め要確認 |
| 保留 | ログイン・ログアウト、権限による出し分け、お気に入り（SCR-003） | 基本範囲の実装要件には含めない |
| 対象外 | 釣行専用の一覧・詳細・登録・編集画面 | 現行設計で廃止。SCR-4xxは欠番のまま維持 |
| 将来検討 | 釣果削除、マスタ編集・削除、管理者専用メニュー、メンバ管理、釣行計画、AI支援 | 旧要求・検討案または未完成の導線があるが、現行の具体的な機能仕様としては未確定 |

`temp` にある釣行一覧・詳細や管理者別画面、AI機能を、そのまま今回の実装必須要件にはしない。リリース単位・納期・開発優先度は承認前であり、第11章の順序は本書の提案とする。

## 3. 用語と主な利用フロー

### 3.1 用語

| 用語 | 英語 | 本書での意味 |
| --- | --- | --- |
| 釣果 | Catch | 釣れた魚やその結果を記録する情報。1件が1匹か複数匹の集計かは要確認 |
| 魚 | Fish | 魚種の情報。個々の釣果とは区別する |
| 釣り場 | Spot | 釣りを行う場所。地図・一覧・詳細から参照する |
| 釣行 | Trip | 釣りに出かけた記録。釣果登録から保存し、必要な情報を各画面で使用する。専用画面・URLは持たない |
| マスタ | — | 魚・釣り場など、入力時の選択や情報参照に使用する基礎情報。管理対象は要確認 |
| 同行者・タックル・道具・水況 | 未確定 | 設計に登場する関連情報。正式名称と入力・表示範囲を要確認 |

根拠：[画面設計 README](./画面/README.md)「ドメイン用語」、[釣果登録](./画面/SCR-103-catch-register.md)課題1・3。

### 3.2 利用フロー

| フロー | 利用者の操作と期待結果 | 未確定部分 |
| --- | --- | --- |
| 地図から探す | ホーム→地図→釣り場の概要→釣り場詳細を確認する | ピンの表現、概要カードを表示する契機 |
| キーワードで探す | 検索→キーワード・条件を指定→魚／釣り場／釣果の結果→対象の詳細を確認する | 検索実行契機、条件、並び順、件数制御 |
| 一覧から探す | ホーム→魚／釣り場／釣果の一覧→選択した対象の詳細を確認する | ナビ「一覧」と各一覧画面の対応 |
| 魚から釣り場を探す | 魚詳細で「直近の釣り場」を参照する | リストから釣り場詳細への遷移と「直近」の定義 |
| 釣果を記録する | ホームの登録ボタン等→釣果登録→必要情報を入力→釣果と釣行記録を保存する | 入力項目、保存単位、完了後の遷移 |
| 釣り場の釣果を見る | 釣り場詳細で最近の釣果を参照し、釣果詳細を確認する | 表示件数、並び順。詳細遷移は個別設計に記載があるが、全体遷移図では仮説 |

根拠：[画面遷移図](./画面/screen-transition.md)および各画面設計。遷移図の実線でも条件表が「仮説」とする遷移は、確定扱いにしない。

### 11.2 要件確定の順序（提案）

1. 基本範囲、釣果一覧の意味、釣果・釣行の記録単位、マスタ追加方式、編集の対象リリースを決める。
2. 入力・表示項目と制約、検索条件、地図の動作、主要導線を確定し、画面一覧・個別設計・遷移図の不整合を解消する。
3. 共通の状態表示、写真、レスポンシブ、非機能目標、運用・データ移行条件を確定する。
4. 各要件IDに対応する受入条件と担当者を定め、要件定義書をレビュー・承認する。

保留機能は採用判断が出るまで受入対象に含めない。現行設計に根拠のある機能でも、未決事項が受入判定に影響する場合は、その回答を記録してから要件を確定する。
